# 2. System Design

## 2.1 High-Level Architecture

```
                         ┌───────────────────────────┐
                         │        Web Browser         │
                         └──────────────┬─────────────┘
                                        │ HTTP :80
                         ┌──────────────▼─────────────┐
                         │   Frontend Container         │
                         │   Nginx + React (Vite build) │
                         └──────────────┬─────────────┘
                                        │ proxy_pass /api/*
                         ┌──────────────▼─────────────┐
                         │   Backend Container          │
                         │   FastAPI + Uvicorn (:8000)  │
                         └──────────────┬─────────────┘
                                        │ SQLAlchemy / PyMySQL
                         ┌──────────────▼─────────────┐
                         │   Database Container         │
                         │   MySQL 8.0 (:3306)          │
                         └───────────────────────────────┘

           All three containers share a Docker bridge network: blog-net
```

## 2.2 Entity-Relationship Design

```
 users                    posts                     categories
 ──────────────           ──────────────             ──────────────
 id (PK)                  id (PK)                     id (PK)
 username (unique)        title                       name (unique)
 email (unique)           slug (unique)                slug (unique)
 hashed_password          content
 role (enum)              summary
 created_at               published
                          created_at
                          updated_at
                          author_id (FK -> users.id)
                                │
                                │  many-to-many
                                ▼
                          post_category (join table)
                                │
                                ▼
                          categories

 comments
 ──────────────
 id (PK)
 content
 created_at
 post_id (FK -> posts.id)
 author_id (FK -> users.id)
```

Relationships:
- One `User` → many `Post` (author)
- One `User` → many `Comment` (author)
- One `Post` → many `Comment`
- `Post` ↔ `Category`: many-to-many via `post_category`

## 2.3 API Design (REST)

| Method | Endpoint | Auth | Description |
|---|---|---|---|
| POST | `/api/auth/register` | Public | Create a new user |
| POST | `/api/auth/login` | Public | Obtain JWT access token |
| GET | `/api/auth/me` | Bearer | Current user profile |
| POST | `/api/auth/promote/{user_id}` | Admin | Promote a user to author |
| GET | `/api/posts` | Public | List posts (filter/search) |
| GET | `/api/posts/{slug}` | Public | Get single post |
| POST | `/api/posts` | Author/Admin | Create post |
| PUT | `/api/posts/{post_id}` | Owner/Admin | Update post |
| DELETE | `/api/posts/{post_id}` | Owner/Admin | Delete post |
| GET | `/api/categories` | Public | List categories |
| POST | `/api/categories` | Author/Admin | Create category |
| DELETE | `/api/categories/{id}` | Admin | Delete category |
| GET | `/api/posts/{post_id}/comments` | Public | List comments |
| POST | `/api/posts/{post_id}/comments` | Bearer | Add comment |
| DELETE | `/api/posts/{post_id}/comments/{id}` | Owner/Admin | Delete comment |
| GET | `/api/health` | Public | Health/readiness probe |

Full interactive schema is auto-generated by FastAPI at `/docs` (Swagger UI)
and `/redoc`.

## 2.4 Container Design

| Container | Base Image | Exposed Port | Purpose |
|---|---|---|---|
| `db` | `mysql:8.0` | 3306 | Persistent relational storage (named volume `db_data`) |
| `backend` | `python:3.11-slim` | 8000 | FastAPI app, runs as non-root `appuser` |
| `frontend` | `node:20-alpine` (build) → `nginx:1.27-alpine` (serve) | 80 | Static SPA + reverse proxy to backend |

Multi-stage build is used for the frontend so the final image only contains
the compiled static assets and Nginx — not the Node toolchain — keeping the
production image small.

## 2.5 CI/CD Pipeline Design

```
push/PR to main
      │
      ▼
 ┌─────────────┐   ┌─────────────┐
 │ Lint backend │   │ Lint frontend│      (parallel)
 └──────┬──────┘   └──────┬──────┘
        ▼                 ▼
 ┌─────────────┐   ┌─────────────┐
 │ Test backend │   │Build frontend│      (parallel)
 │  (pytest)    │   │   (vite)     │
 └──────┬──────┘   └──────┬──────┘
        └────────┬────────┘
                  ▼
        ┌───────────────────┐
        │ Build & push images │   → GHCR (ghcr.io)
        │ (backend + frontend)│
        └─────────┬──────────┘
                  ▼
        ┌───────────────────┐
        │   Deploy stage      │   → deploy hook / SSH pull
        └───────────────────┘
```

Each stage gates the next: a lint or test failure stops the pipeline before
any image is built or pushed, satisfying NFR4.

## 2.6 Security Design
- Passwords hashed with bcrypt (used directly, not via passlib) — never stored or logged in plain text. Passwords are SHA-256 pre-hashed and base64-encoded before bcrypt so the 72-byte input limit never truncates a long passphrase.
- JWT tokens signed with `HS256`, secret injected via environment variable.
- Role-based dependency guards (`require_role`) on every write endpoint.
- CORS restricted at the application layer (open in this demo build; tighten
  `allow_origins` to a specific domain for production).
- `.env` files are git-ignored; only `.env.example` templates are committed.
